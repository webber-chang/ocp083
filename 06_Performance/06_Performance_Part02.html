Mock Exam 3 · Question 15 效能監控與調校

Which three are true about using Database Resource Manager in an Oracle multitenant environment? (Choose three.)

📘 官方解析與重點參考
📝 重點筆記參考：
A. A PDB-level resource plan can limit session PGA memory. (PDB 層級的資源計畫可以限制 session 的 PGA 記憶體)

解釋： 在 PDB 內部的資源計畫中，DBA 可以針對不同的資源群組（Consumer Groups）設定 SESSION_PGA_LIMIT，藉此防止某個單一連線（Session）消耗過多的 PGA 記憶體而影響其他作業。

B. A CDB-level resource plan can limit PDB CPU utilization. (CDB 層級的資源計畫可以限制 PDB 的 CPU 使用率)

解釋： 這是 CDB 層級資源計畫最主要的功能。DBA 可以透過設定 shares (資源份額) 或 utilization_limit (使用率上限)，來控制每一個 PDB 最多能使用多少整體的 CPU 資源，防止某個 PDB 霸佔系統資源（Noisy Neighbor 問題）。

D. PDB-level resource plans can limit uncommitted UNDO per consumer group. (PDB 層級的資源計畫可以限制每個 consumer group 的未提交 UNDO 空間)

解釋： 在 PDB 內部，您可以透過資源計畫設定 UNDO_POOL，來限制某個特定的使用者群組（Consumer Group）可以產生多少尚未提交的 UNDO 資料，避免大型交易耗盡 UNDO 空間。

錯誤選項為何不正確：
C. A CDB-level resource plan can limit session CPU utilization. (CDB 層級的資源計畫可以限制 session 的 CPU 使用率)

為何錯誤： CDB 層級的計畫是針對「整個 PDB」來進行管理的，它不看底層的單一 Session。如果要限制單一 Session（連線）的 CPU 使用量，必須在 PDB 層級 的資源計畫中設定。

E. A CDB-level resource plan can limit PDB UNDO use. (CDB 層級的資源計畫可以限制 PDB 的 UNDO 使用)

為何錯誤： CDB 層級的資源計畫主要用於管理 CPU 和平行處理伺服器（Parallel Execution Servers）。若要限制 PDB 整體的 UNDO 使用量，通常是透過設定 PDB 層級的儲存參數（如 Local UNDO 模式下的表空間限制），而不是透過 CDB-level 的 Resource Plan 來管控。

F. A CDB-level resource plan is mandatory when using PDB-level resource plans. (使用 PDB 層級的資源計畫時，強制必須有 CDB 層級的資源計畫)

為何錯誤： 雖然實務上通常會兩者搭配使用，但 Oracle 並沒有「強制 (mandatory)」規定一定要先建立自訂的 CDB 計畫才能使用 PDB 計畫。如果沒有特別指定 CDB 計畫，系統預設的資源分配機制仍然允許 PDB 內部啟用自己的資源管理。

Mock Exam 3 · Question 27 效能監控與調校

Which three are true about Automatic Workload Repository (AWR) snapshots? (Choose three.)

📘 官方解析與重點參考
📝 重點筆記參考：
這題主要考驗 Oracle 資料庫中 Automatic Workload Repository (AWR) 快照的生成條件與保留策略。以下是針對每個選項的詳細專業解析：
正確選項分析：
A. They are generated if STATISTICS_LEVEL is set to TYPICAL. (如果 STATISTICS_LEVEL 設為 TYPICAL，則會產生快照)
解釋： 正確。TYPICAL 是 Oracle 資料庫 STATISTICS_LEVEL 參數的預設值。在這個設定下，AWR 會自動收集資料庫的效能統計資料，並依據排程（預設為每小時一次）自動產生 AWR 快照。
B. They are generated if STATISTICS_LEVEL is set to ALL. (如果 STATISTICS_LEVEL 設為 ALL，則會產生快照)
解釋： 正確。ALL 會收集比 TYPICAL 更多的統計資訊（例如包含作業系統與 SQL 執行計畫的詳細計時資訊）。在此級別下，AWR 同樣會正常運作並自動產生快照。
E. They can be retained forever. (它們可以被永久保留)
解釋： 正確。AWR 快照的保留天數是可以設定的（預設為 8 天）。DBA 可以透過執行 DBMS_WORKLOAD_REPOSITORY.MODIFY_SNAPSHOT_SETTINGS 套件，將 retention 參數設定為 0。當設定為 0 時，就代表快照將會被「永久保留 (retained forever)」，系統不會自動清除過期的快照。

錯誤選項分析：

C. They are always created automatically. (它們「總是」自動建立)
解釋： 錯誤。雖然 AWR 預設會透過後台的 MMON 行程自動建立快照，但它並非「只能」自動建立。DBA 可以隨時透過執行 DBMS_WORKLOAD_REPOSITORY.CREATE_SNAPSHOT() 來「手動」建立當下時間點的快照。此外，如果參數設為 BASIC，自動建立就會停止。

D. They are always created manually. (它們「總是」手動建立)
解釋： 錯誤。如上所述，AWR 快照在標準配置下（TYPICAL 或 ALL）會依照設定的間隔時間自動產生，不需要人工介入。
F. They are generated if STATISTICS_LEVEL is set to BASIC. (如果 STATISTICS_LEVEL 設為 BASIC，則會產生快照)
解釋： 錯誤。當 STATISTICS_LEVEL 被設定為 BASIC 時，會關閉許多效能收集功能，包含 AWR 的統計資料收集。在此設定下，系統不會自動產生 AWR 快照。

Mock Exam 4 · Question 43 效能監控與調校

A user complains about poor database performance. You want to verify if the user‘s session has waited for certain types of I/O activity. Which view displays all waits waited on by a session at least once?

📘 官方解析與重點參考
📝 重點筆記參考：
V$SESSION_EVENT：
這個檢視表會列出一個 Session 從建立連線以來，只要發生過至少一次 (at least once) 的所有等待事件 (Wait Events)。它會幫你把該事件的發生次數 (Total Waits) 與累積等待時間 (Time Waited) 加總起來。因此，如果你想知道某個 Session 是不是一直在等特定的 I/O 活動，查這裡最準確。
