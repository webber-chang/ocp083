Which three are true about monitoring waits for sessions and services? (Choose three.)

📘 官方解析與重點參考

正確答案解析
⚠️ 注意： 根據您畫面中的題庫解答，它勾選了 B、C、F。但以 Oracle 官方架構與運作機制來說，C 是錯誤的，D 才是正確的。這類題庫經常會有答案錯誤的情況，以下為您提供正確的技術解析：

真理標準答案應為：B、D、F

B. V$SERVICE_EVENT displays all waits for all services if the wait has occurred at least once for a service.（正確）

解析： V$SERVICE_EVENT 會以「服務（Service）」為單位，追蹤並統計該服務所經歷的等待事件。只要該等待事件在該服務中發生過至少一次，就會被記錄在此視圖中。

F. V$SESSION_WAIT and V$SESSION both contain details of the event on which a session is currently waiting.（正確）

解析： 從 Oracle 10g 開始，V$SESSION 視圖整合了等待事件的欄位（如 EVENT、STATE、WAIT_TIME）。當 Session 的狀態為正在等待（STATE = 'WAITING'）時，這兩個視圖都會顯示該 Session 「目前正在等待」的事件詳細資訊。

D. V$SESSION_WAIT and V$SESSION both contain details of the event on which a non-waiting session last waited.（正確）

解析： 如果一個 Session 目前沒有在等待（例如正在 CPU 執行運算），它的狀態會顯示為已等待（如 WAITED KNOWN TIME 或 WAITED SHORT TIME）。此時，這兩個視圖裡的 EVENT 欄位並不會清空，而是會保留並顯示該 Session 「上一次（last waited）」發生的等待事件。

為什麼其他選項是錯的？
C 錯誤（題庫給錯的答案）：

選項說 V$SESSION_WAIT_CLASS 顯示的等待類別統計「僅限於正在等待的 session (only for waiting sessions)」。

真相： 這是錯的。V$SESSION_WAIT_CLASS 記錄的是 Session 連線以來的累計（Cumulative）等待時間分類。不管該 Session 目前是不是正在等待，它都會顯示歷史累計的數據。

A 與 E 錯誤：

這兩個選項都提到 V$SESSION_EVENT 會顯示「過去的（past）」Session。

真相： V$SESSION_EVENT 只會記錄「目前仍連線中（existing）」的 Session 歷史等待數據。一旦 Session 斷開（Disconnect），該 Session 的資料就會從此視圖中被清除（相關時間會被匯總到系統層級的 V$SYSTEM_EVENT）。

Mock Exam 1 · Question 40 效能監控與調校

Which three are true about thresholds, metrics, and server-generated alerts? (Choose three.)

📘 官方解析與重點參考
📝 重點筆記參考：
B. Cleared stateful alerts are displayed by querying DBA_ALERT_HISTORY.（正確）

解析： 警報分為「具狀態 (Stateful)」和「無狀態 (Stateless)」。當一個具狀態的警報（例如：表空間已滿）被解決並清除 (Cleared) 後，它就會從當前的警告視圖 (DBA_OUTSTANDING_ALERTS) 中移出，並歸檔到歷史記錄視圖 DBA_ALERT_HISTORY 中供日後查詢。

C. A space usage management alert is automatically cleared after the underlying problem is resolved.（正確）

解析： 空間使用率警報（如 Tablespace 使用率達 90%）是一種典型的「具狀態警報 (Stateful Alert)」。當 DBA 增加了資料檔大小或刪除了不需要的資料（解決了根本問題），系統偵測到空間降回安全值以下時，就會自動清除這個警報，不需要 DBA 手動去消除。

E. Metrics are statistical counts for a specific unit.（正確）

解析： 這是 Oracle 官方文件中對於 Metric (度量) 的標準定義。Metric 指的是針對特定單位的統計計數或變化率，例如：「每秒的實體讀取次數 (Physical reads per second)」或「每秒的登入次數」。

為什麼其他選項是錯的？
A 錯誤： 選項說「所有的 metrics 都是與執行個體 (Instance) 相關的」。

真相： Metrics 有很多種層級，除了 Instance 級別，還有 Database 級別、Service (服務) 級別、Session (連線) 級別等，並非全部都只跟 Instance 有關。

D 錯誤： 選項說「當表空間達到 97% 滿時，是由 SMON 背景行程來產生警報」。

真相： 負責收集統計資料、檢查閥值並產生「伺服器警報」的背景行程是 MMON (Manageability Monitor)，而不是 SMON。SMON (System Monitor) 主要是負責執行個體復原 (Instance Recovery) 和清理暫存區段等工作。

F 錯誤： 選項說「必須將 STATISTICS_LEVEL 參數設定為 ALL 才能產生警報」。

真相： 要讓 AWR 收集資料並產生警報，STATISTICS_LEVEL 只需要保持在預設值 TYPICAL 即可。設定為 ALL 會收集極度詳細的作業系統與 SQL 執行計畫資訊，通常只在特殊效能調校時開啟，因為它會對系統效能造成極大負擔。

Mock Exam 1 · Question 42 效能監控與調校

Automatic Shared Memory Management is disabled for one of your database instances.
Some SQL statements perform poorly due to excessive hard parse activity, thereby degrading performance.
What would be your next step?

📘 官方解析與重點參考
📝 重點筆記參考：
這題的核心線索在於「過多的硬解析 (excessive hard parse activity)」：

什麼是硬解析 (Hard Parse)？
當使用者發送一條 SQL 語法給資料庫時，Oracle 會先去記憶體裡面找看看有沒有「之前別人跑過、已經解析並產生好執行計畫」的相同語法。如果有，就直接拿來用（這叫軟解析 Soft Parse，速度很快）。如果找不到，Oracle 就必須從頭開始檢查語法、權限並產生執行計畫，這個極度消耗 CPU 資源的過程就是「硬解析」。

為什麼會發生過多硬解析？
這些已經解析好的 SQL 執行計畫，是存放在 SGA 記憶體中的 Shared Pool（具體來說是裡面的 Library Cache）。如果 Shared Pool 的空間太小，舊的執行計畫就會一直被擠出去、清空。當下次再執行相同的 SQL 時，因為記憶體裡找不到了，就只好再次進行「硬解析」，導致系統效能大幅下降。

為什麼答案是 B？

題目特別提到 Automatic Shared Memory Management (ASMM) is disabled。這代表系統「不會」自動幫你把 Shared Pool 調大來解決問題。

身為 DBA，你需要手動調大 Shared Pool 的大小。在瞎猜數值之前，最好的作法就是執行 Memory Advisor for the shared pool (Shared Pool 建議程式)，讓系統根據目前的負載狀況，建議你應該把 Shared Pool 調到多大最合適。

為什麼其他選項是錯的？
A & C (SQL Access Advisor / SQL Tuning Advisor)： 這些工具是用來優化「單一寫得很差的 SQL 語法」（例如建議你建 Index 或改寫 SQL）。但題目說的問題是「硬解析過多」，這是記憶體空間不足導致的系統層級問題，不是單一 SQL 寫不好的問題。

D (Memory Advisor for the PGA)： PGA (Program Global Area) 是給 Session 專用的記憶體，主要用來做資料排序 (Sort) 或 Hash Join，它不負責存放 SQL 執行計畫。

E (Memory Advisor for the SGA)： 因為 ASMM 已經被停用了，你無法再透過整體的 SGA Advisor 來讓系統自動分配，而是必須針對出問題的子元件（也就是 Shared Pool）進行單獨的評估與調整。
