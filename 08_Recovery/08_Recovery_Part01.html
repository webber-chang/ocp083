Mock Exam 2 · Question 4 還原與復原

Which three true about recovering tables using RMAN? (Choose three.)

📘 官方解析與重點參考
📝 重點筆記參考：
Oracle 從 12c 開始引入了 RECOVER TABLE 功能，允許透過 RMAN 將特定的資料表或分區恢復到過去的某個時間點（Table Point-In-Time Recovery）。

正確選項解析：

D. RMAN always uses an auxiliary instance (RMAN 總是使用一個輔助執行個體)
正確。 當您執行 RECOVER TABLE 指令時，RMAN 會在背景自動建立並啟動一個臨時的輔助執行個體 (Auxiliary Instance)。它會將 SYSTEM、SYSAUX、UNDO 以及包含目標資料表的資料表空間還原到這個輔助資料庫中，將其復原到您指定的時間點，接著使用 Data Pump (EXPDP/IMPDP) 將該資料表匯出並匯入回主資料庫，最後自動清理輔助執行個體。

E. RMAN can recover a table after a DDL operation has altered the table structure (RMAN 可以在 DDL 操作改變了資料表結構後，恢復該資料表)
正確。 RMAN 支援在備份完成後至目標恢復時間點之間，資料表曾經歷過 DDL 結構變更（例如 DROP、TRUNCATE 或新增/刪除欄位）的恢復作業。

F. RMAN can recover tables owed by the SYSTEM user (RMAN 可以恢復由 SYSTEM 使用者擁有的資料表)
正確。 只要資料表不是存放在受限的系統表空間中，RMAN 可以恢復 SYSTEM 使用者所擁有的資料表。

錯誤選項解析（RMAN 資料表恢復的限制）：

A 與 C. (RMAN 可以恢復在 SYSAUX / SYSTEM 資料表空間中的資料表)
錯誤。 這是 RMAN RECOVER TABLE 的官方限制：無法恢復存放在 SYSTEM 或 SYSAUX 這兩個系統資料表空間內的任何資料表。

B. (RMAN 可以恢復由 SYS 使用者擁有的資料表)
錯誤。 RMAN 的限制中明確指出，無法恢復屬於 SYS 結構描述 (Schema) 的任何資料表或資料表分區。

Mock Exam 2 · Question 32 還原與復原

Which two are true about instance recovery? (Choose two.)

📘 官方解析與重點參考
📝 重點筆記參考：
C. Setting FAST_START_MTTR_TARGET to a lower value reduces instance recovery time by causing dirty buffers to be written to disk more frequently, thereby reducing the number of I/Os needed during instance recovery.

解析： FAST_START_MTTR_TARGET 參數用來設定「預期的例項復原時間（以秒為單位）」。如果您將這個值設定得較低（例如希望在 30 秒內復原完畢），Oracle 為了達成這個目標，會頻繁地觸發資料庫寫入器（DBWn）將記憶體中的「髒區塊（Dirty buffers）」寫入磁碟。這樣做可以推進檢查點（Checkpoint），減少當機時需要重做（Redo）的資料量，進而減少例項復原時所需的 I/O 次數並縮短時間。

F. It is performed automatically while the database remains in MOUNT state. Then the database is opened.

解析： 當資料庫發生非正常關閉（如斷電或 SHUTDOWN ABORT），下次啟動（STARTUP）時，Oracle 會自動偵測並執行例項復原。這個過程發生在資料庫處於 MOUNT 狀態時（此時控制檔已掛載，Oracle 會比對控制檔與資料檔的 SCN 來決定是否需要復原）。必須先在 MOUNT 狀態下完成「向前推進（Roll forward / Cache Recovery）」後，資料庫才會被 OPEN，允許使用者連線。

❌ 錯誤選項陷阱
A. It is not possible if an archived log is missing.

錯誤原因： 例項復原（Instance Recovery）只需要線上重做日誌（Online Redo Logs），不需要歸檔日誌（Archived Logs）。只有「媒體復原（Media Recovery）」（例如資料檔損毀）才需要歸檔日誌。

B. It is performed automatically after the database is opened...

錯誤原因： 例項復原的核心階段（Roll forward）必須在資料庫 OPEN 之前（也就是在 MOUNT 狀態下）完成。雖然未提交交易的「退回（Rollback）」可以在資料庫 OPEN 後於背景執行，但選項說整個例項復原是在開啟後執行是錯誤的。

D. It is performed by the Recovery Writer (RVWR) background process.

錯誤原因： RVWR（Recovery Writer）程序是專門用來處理 閃回資料庫（Flashback Database） 功能的，負責寫入閃回日誌。負責協調與執行例項復原的背景程序是 SMON（System Monitor）。

E. Setting FAST_START_MTTR_TARGET to a higher value reduces instance recovery time...

錯誤原因： 邏輯完全相反。設定較高的值代表容許更長的復原時間，這會減少日常運作時 DBWn 寫入磁碟的頻率，從而增加例項復原的時間與 I/O。

Mock Exam 2 · Question 34 還原與復原

Which two are true about Oracle instance recovery? (Choose two.)

📘 官方解析與重點參考
📝 重點筆記參考：
E. Recovery begins from the last checkpoint position that was recorded in the control file by the checkpoint process (CKPT).

解析： 例項復原（通常發生在資料庫異常關閉，如斷電或 SHUTDOWN ABORT 後重新啟動時）的第一步是「向前推進（Roll Forward）」。Oracle 必須知道要從重做日誌（Redo Log）的哪個地方開始讀取。這個起點就是「最後一次檢查點（Checkpoint）的位置」。而這個位置是由 CKPT（Checkpoint Process）負責記錄在控制檔（Control File）中的。從這個點開始，所有尚未寫入資料檔的變更都會被重新套用。

F. Recovery reads redo until the end of the redo thread, and then opens the database. SMON then rolls back any dead transactions.

解析： 這是 Oracle 例項復原的標準兩階段標準流程，也是極重要的核心觀念：

Cache Recovery (Roll Forward / 向前推進)： 讀取 Redo Log 直到結尾，把所有資料（包含已提交和未提交的交易）都套用到資料檔中。

Database Open (開啟資料庫)： 當 Roll Forward 完成後，資料庫就會被 OPEN，此時使用者已經可以連線並開始工作。

Transaction Recovery (Rollback / 退回)： 資料庫開啟後，背景程序 SMON 會去尋找那些在當機前尚未提交（Uncommitted / Dead transactions）的交易，並利用 Undo 資訊將它們退回（Rollback）。

❌ 錯誤選項陷阱
A. Recovery begins from the beginning of the CURRENT redo log group.
C. Recovery begins from the start of any ACTIVE redo log group...

錯誤原因： 例項復原的起點是非常精確的「最後一次檢查點位置（Checkpoint Position）」，它可能落在 CURRENT 或 ACTIVE 日誌群組的任何一個位置，而不會死板地從整個日誌群組的「最開頭（beginning/start）」開始讀取。

B. Recovery begins from the last checkpoint position that was calculated by the Database Writer before instance failure.

錯誤原因： 雖然 DBWn（Database Writer）負責將髒區塊寫入磁碟來推進檢查點，但是「記錄」這個檢查點位置到控制檔和資料檔標頭的程序是 CKPT，而不是 DBWn。（選項 E 才是正確的描述）。

D. Recovery reads redo until the end of the redo thread. SMON rolls back any dead transactions, and then the database is opened.

錯誤原因： 順序錯誤！這個選項說「SMON 退回所有死交易後，資料庫『才』開啟」。在 Oracle 的機制中，為了提高可用性（減少停機時間），資料庫會在 Roll Forward 結束後就先開啟（Open），然後才在背景進行退回（Rollback）。（選項 F 的順序才是對的）。

Mock Exam 2 · Question 37 還原與復原

Which two are true about automatic block repair? (Choose two.)

📘 官方解析與重點參考
📝 重點筆記參考：
當資料庫在讀取資料時，如果遇到實體損壞的資料區塊（Corrupt Block，通常會報 ORA-01578 錯誤），Oracle 可以「自動且透明地」透過網路向另一端的資料庫（Primary 或 Standby）索取該區塊的良好複本，並在記憶體與磁碟中進行替換修復，應用程式甚至不會察覺到發生過錯誤。
這個功能的前提是：備用資料庫（Physical Standby）必須啟用 Real-Time Query（即 Active Data Guard 狀態，以唯讀模式開啟並同時套用 Redo）。

✅ 正確選項解析
B. Real-Time Query must be enabled on a physical standby database for automatic block repair to be done on that physical standby database.

解析： 當「備用資料庫（Standby）」遇到損壞的區塊時，它可以自動向主資料庫（Primary）請求一個好的區塊來修復自己。但前提是，這個備用資料庫必須處於 Real-Time Query（Active Data Guard） 狀態下，這個機制才會生效。

E. Real-Time Query must be enabled on a physical standby database for automatic block repair to be done on its primary database.

解析： 反過來說，當「主資料庫（Primary）」遇到損壞的區塊時，它會自動連線到備用資料庫（Standby）去抓取良好的區塊來修復自己。同樣地，作為提供良好區塊來源的備用資料庫，必須啟用了 Real-Time Query 才具備提供此服務的能力。

❌ 錯誤選項陷阱
A. Automatic block repair can repair blocks with no standby database if DB_BLOCK_CHECKING = TRUE.

錯誤原因： 自動區塊修復必須有一個「好的區塊來源」來替換壞區塊。如果沒有 Standby 資料庫，它就沒有地方去抓取備份區塊。DB_BLOCK_CHECKING 只是用來「提早偵測」區塊是否損壞，本身無法無中生有把壞區塊修好。

C. Real-Time Query must be enabled on a primary database for automatic block repair to be done on any of its physical standby databases.

錯誤原因： Real-Time Query 是一個專屬於「備用資料庫（Standby）」的狀態（以唯讀模式開啟並持續套用日誌），主資料庫（Primary）本來就是 Read/Write 正常開啟的，沒有所謂「在 Primary 啟用 Real-Time Query」這種說法。

D. It is not possible for media corrupt blocks.

錯誤原因： 剛好相反。自動區塊修復正是專門設計用來解決「媒體損毀區塊（Media corrupt blocks，即實體磁碟層面的區塊損壞）」的完美解決方案。
