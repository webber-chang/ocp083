Mock Exam 1 · Question 43 Flashback

Which two are true about flashback features in Oracle Database 19c and later releases? (Choose two.)

📘 官方解析與重點參考
📝 重點筆記參考：
beyond=>超過 ,proactively =>主動
A. 當 DB_FLASHBACK_RETENTION_TARGET 的設定值被調低（低於目前日誌已保留的時間）時，Flashback 日誌會被自動清除。

說明： 假設你原本設定保留 24 小時，系統裡存滿了 24 小時的日誌。如果你突然把這個參數改成只保留 12 小時，那麼系統發現有 12 小時的日誌「已經超過你現在的目標」了，它就會自動清理掉那些多出來的、過期的日誌來釋放空間。

C. 當 Flashback 日誌超過 DB_FLASHBACK_RETENTION_TARGET 所定義的保留期限時，系統會在「面臨空間壓力之前」就主動監控並刪除它們。

說明： 這是 Oracle 自動儲存管理的優點。系統是主動（proactively）在做大掃除的，只要日誌過了你的保留期限，它就會把它們清掉，而不會等到 FRA 空間快被塞爆了（space pressure）才手忙腳亂地去清。

為什麼其他選項是錯的？
B 錯誤： 選項說「只有在面臨空間壓力（space pressure）之後，才會刪除超過保留期限的日誌」。

真相： 剛好與選項 C 相反，Oracle 是未雨綢繆的，不會等到空間不足才去清理過期的日誌。

D 錯誤： 選項說「可以透過管理員撰寫的事件觸發程序 (event trigger) 來刪除」。

真相： 清理過期的 Flashback 日誌完全是 Oracle 內部背景行程自動管理的機制，不需要、也不應該由 DBA 去寫什麼觸發程式來做這件事。

E 錯誤： 選項說「只要 DB_FLASHBACK_RETENTION_TARGET 的值被改變，Flashback 日誌就會被自動清除」。

真相： 只有當你把參數調低（如選項 A 所述），導致現有日誌超過新標準時，才會觸發清理。如果你是把參數從 12 小時調高到 24 小時，系統當然不會去清除現有的日誌，反而會開始保留更多。

Mock Exam 9 · Question 19 Flashback

You have an Active DataGuard configuration having one primary and one standby database. The standby database is open in read only mode and in sync with primary. To recover from erroneous transaction, you need to flashback the whole database configuration to a past time. Which methods of flashback operation are correct in this scenario? (Choose two.)

📘 官方解析與重點參考
📝 重點筆記參考：
自動跟隨 (重啟至 Mount)： 當主資料庫執行 Flashback 並以 RESETLOGS 開啟後，會產生新的資料庫化身 (Incarnation)。如果您事先將備用資料庫關閉並重新啟動至 MOUNT 狀態，當備用資料庫的 MRP (Managed Recovery Process) 接收到主庫閃回的標記時，它夠聰明，會自動在背景執行 Flashback 來跟隨主庫，不需要您手動對備庫下達 Flashback 指令。
手動閃回 (安全距離)： 另一個標準做法是 DBA 手動介入。您可以先將備用資料庫手動 Flashback 到「比主庫目標時間點稍微早一點點 (few seconds prior)」的時間。接著主庫再進行 Flashback 與 Resetlogs。當備庫啟動 MRP 後，它會自動向主庫請求並套用新的 Redo，完美接軌。
錯誤選項陷阱分析 (為什麼您的選項不能選)：
...it will flashback the standby database automatically without any additional steps. (您誤選的項目)
錯誤原因： 陷阱在於題幹特別標明了備用資料庫目前是 "open in read only mode" (Active Data Guard 狀態)。Oracle 絕對無法對一個正在開啟 (Open) 狀態的資料庫自動執行 Flashback。如果您沒有做「任何額外步驟 (例如關閉它)」，備庫的 MRP 遇到閃回標記時只會直接中止 (Abort) 並報錯，而不會自動閃回。
Flashback the primary database to required time. Flashback the standby database to few seconds prior to required time.
錯誤原因： 這個順序不佳。如果主庫先 Flashback 並產生了新的化身與日誌，而備庫還在舊的狀態，備庫可能會因為接收不到連續的日誌而發生混亂。最佳實務是先處理備庫 (或讓備庫處於 Mount 準備狀態)，再來 Flashback 主庫。
