Mock Exam 10 · Question 35 Multitenant

Which two are true about Lockdown profiles in a container database (CDB) and its pluggable databases (PDBs)? (Choose two.)

📘 官方解析與重點參考
📝 重點筆記參考：
新題型!!
這是一個標準的「實務與考題預設解答有落差」的陷阱題！

根據 1Z0-083 官方考試的預設解答，您勾選的項目中有一個與標準答案不符。

官方題庫的正確解答是：

☑ A PDB Lockdown profile can be created in an application root. (PDB 鎖定設定檔可以在應用程式根目錄中建立。)

☑ A PDB Lockdown profile can be created in CDB$ROOT. (PDB 鎖定設定檔可以在 CDB$ROOT 中建立。)

💡 專家技術解析與考試生存指南
這題考驗的是 DBA 對於多租戶架構中「權限管控 (Lockdown Profiles)」層級的理解。

為什麼官方答案是這兩個？

集中管理的初衷 (CDB$ROOT)： 在 Oracle 12.2 剛推出這個功能時，Lockdown Profile 只能建立在全域根目錄 (CDB$ROOT) 中。它的設計初衷是讓超級管理員在最上層建立好安全規範，然後套用到下層的各個 PDB，限制他們不能執行某些指令（例如禁止 ALTER SYSTEM 或限制某些網路功能）。

應用程式層級的集中管控 (application root)： 隨著 Application Container 架構的引入，Oracle 允許在「應用程式根目錄 (Application Root)」中建立設定檔，這樣就能統一把安全規範套用到該應用程式底下的所有 Application PDBs。

為什麼您選的 regular PDB 在考試中不能選？

實務上的確可以 (18c/19c 新功能)： 您的觀念在實務上是正確的！從 Oracle 18c 開始，官方確實開放了在一般的 PDB 裡面建立「本機鎖定設定檔 (Local PDB Lockdown Profile)」。

考試的潛規則： 這題是從 12cR2 延續下來的經典考題。在 OCP 考試的語境中，題目沒有特別標示 "Local" 時，它指的通常是可以用來「分發/套用給別人」的公用鎖定設定檔 (Common PDB Lockdown Profile)。這種具有向下約束力的 Profile，只能建立在 CDB$ROOT 或 Application Root。為了順利拿分，請務必記住這兩個「根目錄 (Root)」級別的答案。

錯誤選項陷阱分析 (關於基底設定檔)：

A Lockdown profile created from a base... is always / never automatically modified...

這兩個選項在探討「繼承與連動」。當您使用 CREATE PDB LOCKDOWN PROFILE p2 FROM p1; 時，Oracle 在底層只是做了一個「當下狀態的靜態複製」。未來如果您修改了 p1，這些變更是不會 (never) 自動同步到 p2 的。雖然 never 這個敘述在技術上是正確的，但本題的官方解答邏輯更側重於「建立位置 (Where to create)」，因此標準答案鎖定在兩個 Root 目錄上。

Mock Exam 12 · Question 4 Multitenant

Which two are true about PDB archive files? (Choose two.)

📘 官方解析與重點參考
📝 重點筆記參考：
新題型
在早期的版本，當您 Unplug 一個 PDB 時，只會產生一個 XML 清單檔，您還必須「手動」去複製所有的底層資料檔 (.dbf) 到目標伺服器。為了簡化這個流程，Oracle 引入了 PDB Archive (.pdb 檔)。

正確選項分析：

PDB Archive 的內容物 (...manifest file and all the data files in compressed form...)：
當您在 Unplug 時指定副檔名為 .pdb (例如：UNPLUG INTO '/path/mydb.pdb')，Oracle 會自動將 XML 清單檔與所有相關的資料檔打包，並壓縮成單一個檔案。這讓 DBA 只要搬移一個檔案就能完成 PDB 的轉移，非常方便。

相容性檢查 (DBMS_PDB.CHECK_PLUG_COMPATIBILITY...)：
在將 PDB 插回另一個 CDB 之前，最佳實務是先檢查相容性。這個內建的 PL/SQL 包過去只接受 .xml 檔作為參數，但在支援 PDB Archive 後，它也能直接讀取 .pdb 壓縮檔來進行分析，確認目標 CDB 是否支援這個 PDB。

Mock Exam 12 · Question 8 Multitenant

A container database called CDB1 is OMF-enabled.
PDB_FILE_NAME_CONVERT is not configured in CDB1.
PDB1 was unplugged from CDB1 earlier in the week.
Examine this command, which will be executed in CDB1:
CREATE PLUGGABLE DATABASE pdb1 –
USING ′/u01/app/oracle/oradata/pdb1.xml‘
SOURCE_FILE_NAME_CONVERT =
(′/u01/app/oracle/oradata/‘, ′/u02/app/oracle/oradata/‘);
Which two are true? (Choose two.)

📘 官方解析與重點參考
📝 重點筆記參考：
為什麼必須先 Drop PDB1 (PDB1 must be dropped...)：
當您執行 UNPLUG 指令時，Oracle 會產生一份 XML 檔來記錄 PDB 的中繼資料，但 該 PDB 依然會保留在 CDB 的資料字典中（狀態會變成 UNPLUGGED）。如果您想要用相同的名稱 (pdb1) 重新把它 Plug 回同一個 CDB，您必須先執行 DROP PLUGGABLE DATABASE pdb1 KEEP DATAFILES;，清掉舊有的記錄後，才能執行 CREATE PLUGGABLE DATABASE。

SOURCE_FILE_NAME_CONVERT 的真正用途 (xml does not contain the current locations...)：
為什麼指令中需要加上 SOURCE_FILE_NAME_CONVERT？這個參數專門用來處理「實體檔案在 Unplug 之後，被人為在 OS 層級移動過了」的情境。
也就是說，當初產生的 pdb1.xml 裡面記錄資料檔在 /u01/...，但後來檔案被移走了。為了讓 Oracle 找得到「現在」檔案在哪裡來當作來源，我們用語法告訴它：「請把 XML 裡的 /u01/ 替換成 /u02/ 去找檔案」。這直接證明了 XML 檔內的記錄已經不是檔案現在的真實位置。

錯誤選項陷阱分析 (為什麼您勾選的不能選)：

PDB1 data files already exist in the correct location. (您誤選的選項)

錯誤原因： 如果檔案「已經在未來要運作的正確位置上」，我們在執行 CREATE PLUGGABLE DATABASE 時，會明確加上 NOCOPY 子句，叫 Oracle 直接用原地的檔案。但題目中的指令並沒有 NOCOPY，這代表 Oracle 會執行「複製」動作。加上這台 CDB 是 OMF-enabled (啟用 Oracle 管理檔案)，所以 Oracle 會從 SOURCE_FILE_NAME_CONVERT 算出的來源端，把檔案複製到 OMF 自動決定的新路徑去。檔案現在並不在最終的「正確」位置上。
